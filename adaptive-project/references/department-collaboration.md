# 部门协作与有限委派

沿用 schema 4.0；旧状态没有 delegations 时仍按原权限读取，不自动获得新委派。

部门负责一类交付及其上下文。用户入口收集目标与决策，项目协调者处理全局范围、资源、冲突和最终完成；部门直接承担任务分解、专业协作与指定验收。职责单元是逻辑记录，真实执行仍须绑定获授权的宿主载体。

## 启动时形成可执行分工

发现独立领域、持续工作流、可并行交付或独立核验需求后，先检查现有职责与剩余额度，再建立最小分工。给每个单元明确使命、首批任务、输入、验收者、退出条件与绑定；登记后实际派发。不要固定照搬公司部门，也不要把“建议创建部门”当作已经组织执行。

用户已经授权项目内按需创建长期职责聊天时，可以设置独立项目协调载体与部门聊天，用户入口保留目标决策和里程碑摘要。只有子代理授权时，使用已有会话与子代理；逻辑单元不自动授权新建侧栏聊天。运行时的 `chat.bind` 需要真实宿主返回的 host/thread，不能把子代理 ID 冒充长期聊天。子代理模式沿用宿主协作工具；以下持久部门委派适用于已登记的聊天身份。

正常引导完成后，协调者将首批任务与有限权限交给负责人。部门收到结果或发现本域能力缺口时，先尝试自己推进；只将目标变化、跨域所有权冲突、超额资源需求或无法在现有职责中解决的问题提交协调者。既定分工内的常规交接无需再次向用户申请。

## 自主启动及接续

这是运行项目的默认路径，不依赖用户逐项指定部门或接收方。前台也能使用真实职责聊天，后台计划不是部门协作的前提。

1. 从目标和验收发现独立交付、专业上下文或核验需求，优先复用已有单元与载体。只有短期单次工作时用获授权子代理；仅有一个简单任务时直接执行。若长期聊天创建或互发消息缺授权，说明具体缺口，继续其他已授权工作，不能伪造绑定。
2. 协调者登记最小部门、首批任务、依赖和验收职责。为真实聊天记录 create outbox，创建时只给项目路径、技能位置、使命、原授权来源和“绑定及委派完成前不领取”的初始化要求。收到 READY 是内部交接状态，引导者核实真实回执后自行继续，不要求用户再发启动指令。
3. 通过 outbox.resolve 和 chat.bind 登记真实载体，再 delegation.grant 所需能力、peer_unit_ids 与有限额度。先确保协作双方均可被查找到且验收者具备权限，再首次派发。前台若另建协调聊天，使用不同于 coordinator/operator 的载体登记 ID 将它绑定 coordinator 单元，计入聊天上限并结算创建预留；后台协调载体按 [后台引导](bootstrap.md) 登记，不能混用容量豁免。
4. 按下面的首次派发包发送项目内任务，保留参数和真实宿主回执。部门不再等协调者重述规则：在自身范围拆任务、领取、提交、直接请求验收及处理返工；能力缺口需跨域或超额时再升级。新增本域核验任务是可用选项，不是每个项目必建的第三项任务。
5. 协调者前台以宿主有界等待和局部视图跟进任务至完成、真正受阻或停止条件；部门无需持续空转，等待依赖时结束本轮，由对等部门通过已授权宿主工具直接唤醒。重复消息先查任务/租约/派发状态。只有宿主确实支持时才能承诺唤醒；没有直接寻址能力时明确降级，不能把父代理人工转送称为部门直连。
6. 指定验收者检查当前提交，完成 task.review 后，下游自行领取已满足依赖的任务并使用 accepted_artifacts。协调者核对全局验收、未确认派发、探索关闭与权威交付后 project.complete；仅在确有背景计划时执行相应严格宿主收尾。无工作时不创建新计划维持空转。

### 首次派发包

协调者根据项目实际值组装并执行派发，不把模板交给用户填。每份包都应包含下列可操作信息：

- 项目绝对路径、实际技能/运行时位置、接收方 actor_id、使命与已授予范围；原始用户授权来源引用及其有效范围，不能把协调者消息本身当新增授权。
- 当前任务 ID、输入引用、交付和停止条件；需要验收的任务及对等部门 ID。通过 view.routes 查真实 chat_id/host_id/thread_id，不硬编码试运行地址。
- 默认用 view --actor 与 --task 读相关状态，用 apply --compact 回执；任务 claim 后只写本次 attempt_dir，持有有效租约再续租/提交，详细材料保留文件引用。
- 明确下一步由部门自行执行：提交后 outbox.enqueue/begin，直接调用宿主向指定验收者发送简短任务/版本/引用，再 resolve；收到对等请求后自行核验并接受或返工，不送回协调者代审或转正文。
- 无可执行任务时的等待与接续方式、项目剩余配额/期限和停止条件；有在途工作时不要求用户说“继续”。最终只回传状态、证据引用和必须裁决的问题。

只按需要传这份职责契约及引用，不广播其他部门历史。启动消息应区分“当前已有任务”“接收后需要自主拆分的工作”和“指定验收责任”，避免双方都等待对方派任务。子代理模式使用宿主实际支持的 agent 地址及消息工具，不能套用 chat.bind 或冒充原生聊天。

## 先读局部视图

```text
python -B -X utf8 scripts/runtime.py --project PROJECT view --actor research-lead
python -B -X utf8 scripts/runtime.py --project PROJECT view --actor research-lead --offset 20 --limit 20
python -B -X utf8 scripts/runtime.py --project PROJECT view --actor editor-lead --task chapter-1
python -B -X utf8 scripts/runtime.py --project PROJECT apply --request FILE --compact
```

Python 接口为 `Runtime(project).view(actor, task_id=None, offset=0, limit=20)`。按任务与交接返回的 total 及同一 offset 分页读取职责、相关任务及引用；收件部门可按 outbox 的 task_id 查到相关任务，单任务视图含当前尝试的最后检查点与验收记录。视图不含全量事件与完整历史。事务使用 `apply --request FILE --compact`，只返回 revision/results/replayed，不再载入完整 state 回执。`status`/`read()` 用于独立审计或故障定位。局部视图不是操作系统级数据隔离。

view.routes/routes_total 按同一 offset 分页返回本分支及获准对等部门的 active 聊天 id、unit_id、host_id、thread_id、status，可直接定位接收方，无需协调者转交地址。公共视图保留 authority_sources、scope、limits、execution_mode；单任务视图中的 dependency_summaries 只列依赖 id、revision、status、accepted_artifacts，memories 只返回该任务显式引用的条目。

工作消息只带任务 ID、实体版本、下一步、摘要和文件引用，详细证据保存在项目文件中。先读引用索引，再读取当前决策所需的原文；不要把全量状态、所有历史返回包或原始资料抄回用户入口和协调聊天。

## 登记范围和累计额度

协调者或契约允许的操作员通过事务发放委派。后台协调者仍需当前有效 wake；操作员不能与活动 wake 竞争。例中的证据必须来自实际项目授权与分工记录，数字须取自项目已批准的有限资源。

```json
{"actor_id":"coordinator","idempotency_key":"grant-research-lead","reason":"研究部门承担本域任务与编写部门交接","operations":[{"op":"delegation.grant","id":"research-delegation","chat_id":"research-lead","capabilities":["unit.create","chat.bind","task.create","task.review","recover","outbox.enqueue","outbox.begin"],"peer_unit_ids":["writing"],"limits":{"max_tasks":4,"max_units":1,"max_dispatches":6},"evidence":["inputs/authorization.md","inputs/responsibilities.md"]}]}
```

委派绑定真实聊天，其范围为该聊天所属单元及子树，不能再授权。仅授予所需 capabilities；三项 limits 是非负有限整数，零代表不能消耗该项。全项目的单元、聊天、并发、claim、dispatch、期限与写入限制仍同时生效。另有部门累计任务、新建单元和派发额度；已提交的累计消耗不会因后续失败、撤销或重开退款。被拒绝的事务仍原子回滚，不额外收费。

撤销使用 `delegation.revoke {id, expected_delegation_revision}`，由控制角色提交；保留委派、用量和已发生操作的历史。同一聊天不能换 ID 重新发放委派来重置额度。跨域合并前须撤销源部门的活动委派，控制角色再用 unit.merge 转移未结束任务的责任和验收引用；旧委派保持 revoked。仍承担未结束任务验收的单元不能直接退休。工作者不能给自己发授权、代用协调身份或复制协调者 wake 凭据。

| 委派操作 | 部门边界 |
| --- | --- |
| unit.create | 仅在本部门子树中创建，继续检查项目组织授权、深度与全局容量 |
| chat.bind | 仅绑定本分支的已核实载体；真实创建仍需原项目长期聊天授权 |
| task.create | 仅为本分支创建任务，不替其他部门强行分配任务或变更其所有权 |
| task.review | 任务的 reviewer_unit_id 位于本委派范围，且不能验收自己提交的成果 |
| recover | 必须指定本分支 task_id；只恢复过期凭据，不能抢占有效租约 |
| outbox.enqueue / outbox.begin | 只处理自身意图；创建聊天限本分支，跨部门消息目标须在 peer_unit_ids 内 |

`task.create` 可明确 `reviewer_unit_id`；省略时默认责任单元。负责人新建任务时，验收部门须在自己的分支或 peer_unit_ids 中。存在独立验收需求时，在执行前指定验收部门，并为其负责人登记 task.review 权限。部门负责人可按当前任务的验收条件接受或返工，无需让协调者转录审查正文；项目完成仍由控制角色核对全部章程验收。正式记忆生效、探索方向、全局所有权调整、暂停/恢复、预算和宿主调度保留原控制权限。

## 直接交接与可靠派发

跨部门消息由发送部门登记 outbox，直接调用已授权宿主消息工具。发送目标须为本项目真实绑定，不能从任意消息中继承权限。接收方读取当前任务和证据，按自己的职责创建或领取工作；合作请求不构成强制改派、修改接口或扩展授权。

```json
{"op":"outbox.enqueue","id":"research-to-writing-1","kind":"send_message","payload":{"chat_id":"writing-lead","task_id":"chapter-1","summary":"研究证据已就绪；请按任务当前版本检查引用和已验收输入，再领取编写任务。","refs":["evidence/research-summary.md"]}}
```

部门 send_message 的 payload 必须带 task_id 和非空 summary（最多 2000 字符），refs 可带本地证据引用并保存哈希；create_chat 不要求 task_id/summary。任务须属于发送或接收部门范围。文件存在或消息已到达不等于成果通过验收；依赖任务仍须 done 才能作为已验收依赖启动下游。

调用前以当前 outbox revision 提交 `outbox.begin`，成功后只执行一次宿主操作，再用原发送身份提交 `outbox.resolve`。未知结果先查询宿主并 `outbox.reconcile`，不盲目重发。全局派发预算和该部门派发额度同时扣减。协调者可对账，但不需要成为消息正文的中转者。

暂停后部门不得创建、领取、验收或发起新派发；允许为自己的既有意图补登记 resolve/reconcile，以记录暂停前已经发生或仍不确定的宿主结果。这不允许执行新的宿主动作，也不解除暂停。恢复前重读委派、原绑定、期限、累计用量、未确认 outbox 与任务租约，不恢复旧凭据或重置额度。

## 一个完整的分工例子

用户要求完成带证据的入门指南，并已授权本项目职责聊天协作。协调者发现研究与编写有独立上下文，复用或建立这两个单元，登记真实载体、首批任务与有限委派。研究任务由研究部门负责、编写部门验收；编写任务依赖该研究任务并由研究部门核验引用。

研究负责人在自己的领域创建资料核查任务，提交后直接把摘要和引用发送给编写负责人。编写负责人读取原始证据，对指定研究任务验收，再领取依赖已满足的编写任务；完成后直接交给研究部门核验引用。双方处理本域返工，协调者接收“已完成什么、证据在哪里、哪些事项需裁决”的短摘要，最后核对全局交付。

上述指南例子是协议示意。一次独立的本地工单试运行已观察到：协调者自建两个部门并首次派发，部门自主追加核验任务、四次真实直连、三项交叉验收，根没有业务救援。16 个真实命令配对样本中，精简运行时 JSON 为 92,072 字节、同点完整状态为 773,752 字节；这只证明该次运行时输入体量减少 88.1%，不是总上下文/token或跨项目承诺。运行时测量包装器及完整快照是该次审计手段，日常使用直接用 view/apply --compact，不要求复制试验包装器、固定部门数量或观测阈值。

未来行为验收应只给普通项目目标和有效授权，核实是否无需额外提醒就发生实际创建、派发、对等消息和验收；记录未通过或降级，不复制旧项目状态、授权和成功结论。
