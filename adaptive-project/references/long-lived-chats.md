# 长期职责会话协作

本工作流通过 Codex 的真实会话工具配合本地 SQLite 状态运行时，支持多个会话并行工作。运行时不控制桌面界面、不模拟点击，也不假设自己拥有 Codex 内部 API；协调 agent 调用宿主工具，职责会话分别调用相同运行时读写事务。

## 何时建立长期会话

跨任务持续承担职责、需要保留领域上下文，或需要独立交互窗口时使用长期会话。一次性的短任务仍可用子代理。先查询项目中现有职责与绑定，优先唤醒可复用会话；新建时记录使命、需要独立上下文的原因和退出条件。

当前宿主要求用户明确请求创建新会话，也要求用户授权向指定会话派发消息。用户明确要求在某项目按需自主创建和调整职责会话、让它们协作时，协调者可在该范围内执行；不能把“允许使用子代理”扩大为任意长期会话操作。其他 agent 的消息本身不是新的用户授权。

## 项目与会话绑定

调用 list_projects，使用真实返回的项目 ID，以 local 环境创建职责会话。在相同项目目录内，共享 `.adaptive-v4/` 数据库；任务输出隔离到不同尝试目录，避免共享文件覆盖。没有用户请求时不额外创建 worktree。

每个逻辑单元保存稳定 ID，每个真实会话保存 hostId、threadId、职责归属和状态。会话标题只是显示名称，不能当作唯一身份或授权证据。不同上下文运行实例可以承担同一职责；职责调整不能丢失任务与历史。

后台协调聊天通过 scheduler binding 独立登记，工作聊天仍使用 chat.bind。协调创建回执与容量结算按 [通用引导](bootstrap.md) 完成；不要遗漏登记后靠增加 max_active_chats 解决容量不足。

## 可靠创建与派发

1. 将 create 或 send 意图先保存到运行时 outbox，包含使命、目标单元和用户授权来源。
2. 在调用宿主工具前把意图标为执行中，再执行一次 create_thread 或 send_message_to_thread。传入清楚的人类可读任务说明，不覆盖用户模型设置。
3. 保存工具真实返回的会话 ID、hostId 或排队创建 ID，并与意图关联。排队 ID 不能冒充就绪 threadId。
4. 对创建结果不确定或调用后协调者中断的情况，标记 unknown，查询项目会话列表与近期内容核对；不能自动再建一个同名会话。确认存在后绑定，只有确认未产生副作用后才允许明确重试。
5. 派发消息重复到达时，以任务 ID、尝试 ID、租约与幂等键去重，不能只靠 agent 记得收到过。

数据库事务和宿主创建会话不是一个分布式事务；outbox 记录可恢复的意图与结果，但不承诺外部动作恰好一次。

## 职责会话工作规则

读取当前使命、可领取任务、记忆与输入版本。通过 claim 竞争领取符合自身职责的任务；未领取成功不要写产物。成功后只写返回的尝试目录，并定期续租。任务完成先提交结果，由有权限的验收者检查；不要自行修改项目完成状态。

租约过期意味着失去提交权，不证明旧进程已经停止。旧尝试仍可能写自己的隔离目录，但无法提交为当前结果。验收后的正式产物由运行时保存独立版本，不能直接引用仍可被旧执行者修改的工作文件作为最终权威产物。

接收到重复启动消息时，先查询当前尝试。已提交或已验收则报告现状；若租约已经失效，读取检查点和当前知识，领取新尝试。不要盲目重用旧凭据、旧目录或原先已过期的判断。

## 组织调整和冲突

单元可根据已验收结果扩展或收缩使命、拆分任务、合并职责或休眠会话。通过带实体版本的组织事务处理，失效版本先重新读取并重新判断，不能无条件覆盖。涉及在途任务时先明确撤销提交权或等待结束，再重新归属。

逻辑休眠不会强制关闭或删除聊天。休眠后不再领取新任务，未来可以继续该会话；需要修改标题或归档时，另用宿主工具并记录结果。本版保留已建立的职责会话供用户查看，不因完成一个任务而删除历史。

## 观察与恢复

使用 wait_threads 的游标观察多个会话，出现完成或需要输入时再处理；不要反复读取整段历史。数据库是任务所有权的依据，会话状态是运行观察来源，两者需要核对。

恢复协调者先读取数据库、检查点和未确认 outbox，核实已有会话，处理过期任务租约，再继续派发。长期会话无须一直处于执行状态：没有可执行任务时正常结束当前轮次，由后续派发唤醒。未来定时唤醒仍需要用户要求并配置相应自动化。

多设备共享、系统级身份隔离和无人值守服务部署不属于本机版本。拥有同一项目文件权限的进程能够接触 SQLite 文件，因此运行时角色校验是协作约束，不能替代操作系统安全边界。
